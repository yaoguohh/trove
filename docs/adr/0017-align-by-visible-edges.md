# 0017 对齐按看得见的边：图标看中线、文字看起点，用测量脚本验收

- 状态：已采纳
- 日期：2026-11-23
- 依据：用户要求把全局的间距、位置和图标居中量一遍；实测见"背景"

## 背景

用户觉得界面"差一点精细"，但说不出是哪里。在 2 倍渲染图上按看得见的像素量了面板、状态菜单、欢迎窗口、
空面板、Peek 气泡和应用图标，偏差都在 1–7pt，眼睛只觉得不对，指不出位置：

- 卡片标题从 12.0 开始，正文和底栏从 15.1、14.5 开始：标题的左边距是 `圆角 × 0.82`，另两处是圆角。
- 来源图标的可见右边距 11.6，底栏序号 15.0：应用图标四周自带约 10% 的透明边，布局按画布排，看到的
  边就往里缩了。
- 工具栏的"⋯"比它的 28pt 方框中心偏右 3.9pt：`.borderlessButton` 菜单样式自己画控件，不按标签的框排，
  也不用标签设的字号和颜色。
- 状态菜单的文字起点有 5 条线（39.3–46.5），图标中线相差 2.0pt，右侧可见边从 14.0 到 20.5：每一种行
  各写各的内边距和间距。
- 欢迎窗口"用法"的文字从 70.6 开始，权限卡片里从 76.4 开始。
- 链接卡的标题首行比旁边图标的中心高 3.9pt：两者顶对齐。
- Peek 气泡的展开提示压在文字区右上角 5×8pt 的范围里；单行时文字下方空出约 32pt。
- 应用图标的底板比 macOS 图标网格大 6%，圆角是普通圆弧；macOS 14、15 按原样显示，比旁边的图标大一圈。

问题的来源有三类：同一件事各处写各的数；布局框和看得见的边不一致（透明边、字号自带的行距、系统控件
自己排版）；对齐靠目测。

## 决定

- **规则**：图标看中线，文字看起点；左右各一个内边距；布局框就是看得见的边；描边不占位置。写在
  DESIGN.md"对齐"一节。
- **布局常量集中**：决定对齐的列宽和内边距写在每个界面的常量里（`CardMetrics.contentInset`、
  `StatusMenuView.Layout`、`WelcomeView.Layout`、`PeekController` 的提示列），视图从常量推出位置。
  例如欢迎窗口权限行的图标列宽 = 用法方块宽 − 卡片内边距，两组文字因此从同一条线开始。
- **去掉透明边**：应用图标用 `AppIconImage` 按可见的圆角方形排；空面板的大符号用 `.resizable()` 按框
  定尺寸。
- **验收**：`scripts/audit-layout.sh` 跑可选的 `LayoutAuditTests`，渲染各界面，按像素量出对齐线、
  中线和边距，期望值直接读上面的常量。偏差超过 0.5pt 记 ✗，文字和符号的边缘放宽到 1.5pt（字形自带的
  左右留白随字母变），有 ✗ 时脚本返回非零。
- **应用图标**：按 Apple 网格重画，824/1024 的连续曲率圆角方形，画面在其中居中，去掉看起来像划痕的黑色
  弧线。

改后全部测量项都在容差内。

## 放弃的方案

- **只看截图调**：这次的偏差大多 1–4pt，看得出不舒服，看不出差在哪，也没法确认改对了。
- **读辅助功能树里的元素位置**：测试进程不受信任时 SwiftUI 不建辅助功能树；即使能读，读到的也是布局框，
  正好漏掉透明边和字形留白这类问题。
- **逐个微调偏移量**：比如给"⋯"加 −3.9pt 的偏移。换字号、换语言或系统更新后就不对了，问题的来源还在。

## 后果

- 状态菜单的行之间不再留 2pt 缝，分组之间统一 8pt，整体矮了约 20pt。
- "⋯"按代码里写的 17pt、`t2` 颜色显示，比原来系统画的大一些、暗一些。
- 来源图标的可见大小不变（29pt）；取不到图标时的首字母方块随之从 36pt 缩到 29pt，和真图标一样大。
- 测量依赖渲染：渲染时去掉玻璃，Peek 放在黑底上量（深色阴影否则会被当成气泡的一部分）。窗口要真的显示
  在屏幕上，所以不进 CI。
- 符号与文字的中线对齐有 0.5–0.6pt 的残差（`link`、`command`、`trash`），来自符号在自己框里的位置，
  按 0.75pt 的容差接受。

## 什么时候重新考虑

- 加了新界面或新的一类行：先把它的列宽和内边距定成常量，再把测量加进 `LayoutAuditTests`。
- 系统更新后 SF Symbol 或系统控件的排版变了，测量出现成片的 ✗。

# 0005 存储：单个 JSON 文档加 sidecar 文件，按内容身份去重

- 状态：已采纳
- 日期：2026-06-08（sidecar）；2026-10-30（图片直存）；2026-11-13（内容身份、文档版本、注入根目录）
- 依据：`db7820d`、`0189ec2`、`20980b0`；本分支 `3894801`、`4dea6a8`、`4321208`

## 背景

历史默认 500 条（可调到 50–5000），内容从一个单词到几 MB 的表格都有。早期大内容会拖慢界面并撑大
`history.json`；图片曾在主线程做 TIFF → PNG 编码，4K 截图要卡近 1 秒；去重借用显示文字，图片之间会被
误判为重复，撤销删除时丢图。

## 决定

- 整个历史存成一个 `history.json`（带 `version` 字段），图片和超长文本存成 sidecar 文件：
  - 文本去掉首尾空白后超过 2 万字符时，全文写进 `texts/<id>.txt`，JSON 里只留前 2 万字符；超过 500 万字符
    时截断并标记。
  - 图片原样存 PNG（TIFF 才转码），另存不超过 640px 的缩略图；编码与写盘都在后台。
- 每条 Clip 有一个内容身份 `contentHash`：文本取规范化后文本的 SHA-256，图片取 PNG 字节的 SHA-256。
  新增与撤销删除只按它去重，保证一份内容只有一张卡。
- 去抖 0.3 秒后在串行队列里写盘；格式变化在解码时迁移，加载后写回一次。
- 文件位置由注入的 `ClipFiles` 决定，测试用临时根目录。

## 放弃的方案

- **SQLite / Core Data**：在 500 条、单进程读写的规模下，单文件 JSON 足够快，且便于人工查看和备份；
  格式细节已隔离在 `HistoryPersistence` 里，以后换存储只动这一层。
- **全部内容内联**：大内容会让每次写盘重写几 MB。

## 后果

每次变更都会全量重写 `history.json`。在默认上限下单个文件约几 MB，可以接受。

## 什么时候重新考虑

用户普遍把上限调到几千条、或 `history.json` 常态超过 20 MB 时，改用 SQLite；那时可以顺带做全文检索。

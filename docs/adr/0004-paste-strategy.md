# 0004 粘贴：先用辅助功能直接插入，其次只抬前窗，最后合成 ⌘V

- 状态：已采纳
- 日期：2026-06-15（不抑制键盘）；2026-06-22（AX 优先）
- 依据：`b6a5807`、`5a7b9fb`；本分支 `07a93b8`

## 背景

选中卡片后，内容要进入唤出面板之前的那个输入框。直接激活目标应用再发 ⌘V 有两个问题：
`NSRunningApplication.activate` 自 Big Sur 起会把目标应用的所有窗口都抬到最前（浏览器的其他窗口会盖上来）；
发送 ⌘V 前后抑制键盘会吞掉用户紧接着按下的真实 ⌘C。

## 决定

唤出面板时记下最前面的应用和它的焦点元素（`PasteTargetSnapshot`，90 秒内有效）。粘贴时依次尝试：

1. 不激活目标，用辅助功能接口把文本写进焦点元素：先设 `AXSelectedText`（替换选中部分），不支持再改写
   `AXValue` 并移动光标。成功则窗口顺序完全不动。
2. 失败（例如密码框）就只抬起目标应用的最前窗口：通过 `dlsym` 取得 Carbon Process Manager 的
   `SetFrontProcessWithOptions` 并带上"只抬前窗"选项；取不到再退回 `NSRunningApplication.activate`。
   然后再试一次第 1 步。
3. 仍不行就合成 ⌘V：使用 `combinedSessionState` 事件源，带上明确的修饰键标志，不抑制本地键盘事件。

图片只能走第 3 步。没有辅助功能权限时只把内容写到剪贴板。

## 放弃的方案

- **一律激活后发 ⌘V**（Maccy、Clipy 的做法）：会抬起目标应用的全部窗口。
- **设置应用级的 `kAXFrontmostAttribute`**：同样会抬起全部窗口。

## 后果

- 第 1 步绕过了目标应用自己的粘贴处理和撤销记录；对大多数原生文本框没有区别。
- 有些应用对 `AXSelectedText` 返回成功却没有真正写入（怀疑部分 Electron、浏览器富文本框和终端），这时
  用户看到"没有粘贴上"。日志分类 `paste` 会记录每次实际走的策略。

## 什么时候重新考虑

确认某类应用存在"回报成功但没写入"时：在第 1 步之后读回焦点元素的值核对，不一致就继续走后面的步骤，
而不是为个别应用加特判。
